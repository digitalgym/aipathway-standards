# AIP-BS-BAS-READY-CHECK: bas-ready-check-build-standard

**Source of truth:** https://aipathway.com.au/explore-ai/bas-ready-check-build-standard (edition 2026-11-12)
**Markdown:** https://aipathway.com.au/explore-ai/bas-ready-check-build-standard.md
**Checks as data:** https://aipathway.com.au/explore-ai/bas-ready-check-build-standard/checks.json

This file points at the specification; it does not copy it. The standard is
published and versioned elsewhere, and when its edition moves this folder is
rebuilt from it, not patched. Read the Markdown before anything else.

## What and why

Eleven of these thirteen checks run on your own machine, against the stub, before you talk to anybody. The last one is a live tenant, and that one runs against your own live systems. One is not a software check at all: it asks what you measured before you started.

## Requirements, as the checks the build is held to

- **period-from-the-ledger** The period's transactions come from the ledger, by its own ids and dates. The list covers exactly the BAS period the business set, read from the ledger the business runs: every transaction dated inside the period, by the ledger's own transaction id. A transaction dated outside the period is not flagged as if it were in it, and nothing is read from an export somebody edited.
- **every-flag-cites-its-source** Every flag cites the transaction it came from, and that transaction reads back. Every flag on a line names the ledger's transaction id, and that id reads back from the ledger with the same date and total the flag states. A flag about the whole period (a swing, a control account difference) names the period and the figures it compared, read from the ledger. A flag that cannot point at its source is dropped, not shown.
- **tax-invoice-held** GST claimed above the tax invoice threshold with no tax invoice attached is flagged. A purchase above the threshold the business set (the ATO figure, dated on this page) with a GST credit claimed and no document attached in the ledger is flagged, citing the transaction. Below the threshold it is not flagged. Where the ledger cannot say whether a document is attached, the check is listed as not run, never assumed either way. An attachment is not proof of a valid tax invoice; the flag is for a person to look at.
- **code-differs-from-usual** A GST code that differs from what that supplier or account usually carries is flagged, with the usual code shown. For each purchase line, the GST code is compared with the code the same supplier, or failing that the same account, carried on most of its lines in the history the business set. A line coded differently from a clear usual code is flagged with the usual code and how many lines it was seen on. Too little history means no flag, never a guess. The flag says the code is different; it never says which code is right.
- **gst-on-no-gst-accounts** GST claimed on an account the business marked as carrying no GST is flagged. The business, or its BAS agent, lists the accounts that carry no GST in its own books: typically wages, super, bank fees and interest. A line in one of those accounts with a GST credit claimed is flagged, citing the transaction. The list is the business's setting; the build never decides on its own that an account carries no GST.
- **capital-coded-capital** A purchase in a capital account not coded capital, or the reverse, is flagged when the business reports G10 and G11. Where the business reports capital and non-capital purchases separately (full reporting), a purchase line in a fixed asset account carrying a non-capital GST code is flagged, and so is a line in an expense account carrying a capital code. Which account is capital is the business's own chart of accounts. Under simpler BAS, where those labels are not reported, the check is listed as not run.
- **unreconciled-and-uncoded** Transactions inside the period that are unreconciled or carry no tax code are flagged. Every bank transaction dated in the period that the ledger shows as unreconciled is flagged, and so is every bill, spend or receive line in the period with no tax code at all (a manual journal is left to check 9). Where the ledger cannot say whether a line is reconciled, that half of the check is listed as not run.
- **swing-against-comparable** Period totals that swing against the comparable period beyond the business's band are flagged, with both figures. Total sales, GST on sales and GST on purchases for the period are compared with the comparable period the business set (usually the same quarter last year), each read from the ledger the same way. A move larger than the band the business set is flagged with both figures, both periods and the change. A swing is a question for a person, not an error.
- **control-account-agrees** The GST control account's movement for the period is compared with the GST the transactions report, and a difference is flagged. The movement in the GST account for the period is read from the ledger and compared with GST on sales less GST on purchases for the same period (from the ledger's GST report where it offers one, otherwise from the coded lines, and the list says which). A difference is flagged with both figures and, where they can be found, the transactions posted straight to the GST account.
- **lists-what-it-could-not-check** Whatever it could not check is listed, with the reason. A check the ledger cannot support (no way to read attachments, no reconciled flag, no GST report), a check the business's reporting makes irrelevant (capital under simpler BAS), and a check with too little history is listed under not checked with the reason. Nothing is silently skipped, and nothing is flagged on a guess about data that could not be read.
- **flags-never-decides** Read only: one list to the named person, nothing written, nothing lodged, no advice. The list goes once per run to the bookkeeper or BAS agent the business named. Nothing is written to the ledger: no code changed, no journal posted, no attachment added, nothing lodged. A flag states what was found and why it was flagged; it never says what the code should be, what to claim or how to fix it. The person decides.
- **survives-the-builder** It survives the builder. Someone other than the builder can explain what it does, and it runs on an account the business owns.

## Out of scope for the build, by design

- **pass-test** The pass test passes: not provable on the stub, reports `with_us`; proved on your own systems, with the evidence attached.

When a check is `with_us`: No hosted step, and no product runs this one. The build connects straight to the business's own Xero, MYOB Business or QuickBooks Online through that ledger's own sign-in and API, read only. The production check runs there: a seeded line caught by its real id, every cited id read back, and the ledger's own audit trail showing the run wrote nothing. Keeping that read authorised every quarter, and each client's history of usual codes, is the step that needs care; it is the business's own, or a scoped build. There is nothing to buy: your build does this step on the business's own systems. No production run is offered yet, because the live port map is not published, so do not run AIPATHWAY_ENV=production. Run the pass test by hand on the real systems and attach the evidence.
