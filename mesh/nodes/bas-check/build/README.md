# BAS Check: build and conformance harness

BAS Check runs before each BAS period is lodged, built to
AIP-BS-BAS-READY-CHECK 2026-11-12. On its schedule it lists the client files
whose period has ended, reads each period from the client's ledger (Xero,
MYOB Business or QuickBooks Online) read only, with the history before it and
the same period last year, and hands the bookkeeper or BAS agent named in the
settings one list: Ready, or Not ready with the GST exceptions to look at.
GST claimed above the tax invoice threshold with nothing attached, a code
unlike the supplier's or account's usual one (the usual code and its count
shown), GST on an account marked as carrying no GST, capital coded
non-capital under full reporting, uncoded and unreconciled lines, swings
against the comparable period, and a GST account that does not agree. Every
line flag cites the ledger's transaction id, read back with its date and
total, and carries its as-of time; a flag that does not read back is dropped.
What the ledger could not be read for is listed under not checked, with the
reason, and never guessed.

It never writes to the ledger, never changes a tax code, never locks the
period, never lodges and never gives tax advice. The registered BAS or tax
agent, or the business itself, decides on each flag and lodges.

Per ledger, as at 2026-11-12: all three are read over their own API, read
only. None lodges a BAS over these APIs. Lock dates are not writable over the
Xero or MYOB APIs (QuickBooks unconfirmed), so locking the period stays with
the person. MYOB has no reconciled status and QuickBooks no reconciled flag or
Australian GST report through the API, so those parts are listed as not
checked, or worked out from the coded lines and said so.

    npm install
    node run.mjs        # the conformance run; writes manifest.json and envelope.json
    node mutants.mjs    # every scenario must go red for a do-nothing build and a broken one

The committed evidence is in ../evidence/bas-ready-check/.

# bas-ready-check-build-standard: conformance harness

Generated by `npx @aipathway/conformance init bas-ready-check-build-standard`.

    npm install
    node run.mjs

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## This standard

13 checks: 11 provable here on the stub, 1 only in
production, 2 partial, 1 preconditions needing evidence rather than code.

The checks are fetched at run time from https://aipathway.com.au/explore-ai/bas-ready-check-build-standard,
so a correction published there reaches you without a release here.

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

This standard has no hosted provider, so `conformance connect` does not apply to it.

No hosted step, and no product runs this one. The build connects straight to the business's own Xero, MYOB Business or QuickBooks Online through that ledger's own sign-in and API, read only. The production check runs there: a seeded line caught by its real id, every cited id read back, and the ledger's own audit trail showing the run wrote nothing. Keeping that read authorised every quarter, and each client's history of usual codes, is the step that needs care; it is the business's own, or a scoped build. There is nothing to buy: your build does this step on the business's own systems. No production run is offered yet, because the live port map is not published, so do not run AIPATHWAY_ENV=production. Run the pass test by hand on the real systems and attach the evidence.

The checks that never go green on the stub report `with_us`.
