# Balance Proof: conformance harness for two-records-build-standard

Balance Proof ties every balance sheet account in Xero to the document that
supports it, each month, to AIP-BS-TWO-RECORDS. Source a is the month's support
file (bank, loan and hire purchase statements, the ATO integrated client
account, payroll liabilities and super reports, the fixed asset register), each
document tagged with the Xero account it supports. Source b is Xero's balance
sheet at month end. They join on the Xero account id only, never on an account
name or an amount.

A balance in Xero with no document behind it is an orphan for the senior
accountant: that is the list of balances nobody can explain. A balance that
differs from its document is a Difference with both values and the master's
value. A correction (in Xero, a draft adjusting journal) is written only after
a named person accepts it, and the accountant posts it. Every run publishes its
counts, the all-clear included.

The ports carry the pair as the standard's stub names them: `read_job` reads
source a (the support file), `read_ledger` reads source b (Xero) and the
contract.

Generated by `npx @aipathway/conformance init two-records-build-standard`.

    npm install
    node run.mjs

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## This standard

12 checks: 10 provable here on the stub, 1 only in
production, 1 partial, 1 preconditions needing evidence rather than code.

The checks are fetched at run time from https://aipathway.com.au/explore-ai/two-records-build-standard,
so a correction published there reaches you without a release here.

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

This standard has no hosted provider, so `conformance connect` does not apply to it.

No hosted step. The production check runs over the business's own two sources with a person on every correction. There is nothing to buy: your build does this step on the business's own systems. No production run is offered yet, because the live port map is not published, so do not run AIPATHWAY_ENV=production. Run the pass test by hand on the real systems and attach the evidence.

The checks that never go green on the stub report `with_us`.
