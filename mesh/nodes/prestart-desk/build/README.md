# Prestart Desk: exception-desk-build-standard harness

Prestart Desk is an exception desk whose main source is the daily check. A
tech does the vehicle pre-start check, or the site safety check on a job, in a
form app that emails the completed form to the checks mailbox. The desk reads
the vehicle (a plant and equipment asset in Simpro) or the job by the id on
the form, files the check as an attachment on it, and counts it filed only
when an attachment id reads back. A check with no id, or an id Simpro does not
hold, goes back to the tech who did it.

Every failed item goes in front of a named owner with a clock: one item per
vehicle or job, type `other` with `vehicle_check_failed` or
`site_check_failed` kept, the owner and the clock from the routing table the
business wrote (a label row lets failed vehicle checks go to whoever looks
after the vans and failed site checks to the site supervisor). Tomorrow's
check failing again updates the same item and keeps its clock; a check that
passes marks it resolved upstream, and it stays open until the owner closes it
with what was done. The desk never takes a vehicle off the road, never clears
one to drive and never closes an item. Late items escalate once; the morning
summary goes out at the set time, also when it is empty, and lists every
vehicle or job with failed items still open.

| file | what |
|---|---|
| `build.mjs` | the desk: check filing, intake, escalation, summary |
| `check-world.mjs` | the stub world: Simpro jobs and vehicle assets, Xero, checks mailbox, Raise tab, routing, queue |
| `scenarios.mjs` | one scenario per check, each read off the recorded trace |

Every check was run against a do-nothing build and eighteen single-fault
builds (record not read, check not filed, new types, owner from the form,
label routing ignored, no dedupe, clock restarted, failed items not updated,
auto-close, resolved mark dropped, a passing check raised, dispute escalated
past its owner, escalation every run or early, no empty summary, summary
early, failed checks missing from the summary, owner told from a suggestion)
and goes red for at least one of them.

## The three files

| file | whose | what |

| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

Office Voice holds the one queue: a sheet, a bot or a flow raises items with raise_exception and reads them with list_exceptions, beside the items its own calls hand off. The owner and due time come from the business's routing table, raising the same record and type again updates the open item, and only a person closes an item, with an outcome, on the Exceptions page, unless the owner switched that type to close itself. Office Voice shows which items are overdue but does not yet escalate them, so the escalation stays with the business. Call it on the Office Voice MCP (office_voice.raise_exception): the owner mints a key at office-voice.com/app/keys with the scope the tool names, on any Office Voice account. There is no production run of these checks yet, so the stub run is the finished build; AIPATHWAY_PROVIDER=office_voice.raise_exception needs a live port map that is not published. Do not hand-roll the write.

The checks that never go green on the stub report `with_us`.
