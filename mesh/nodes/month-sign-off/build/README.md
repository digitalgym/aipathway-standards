# Month Sign-Off: build and conformance harness

Month Sign-Off closes the month for each client file, built to
AIP-BS-MONTH-END-CLOSE 2026-11-12. On a schedule after month end it works the
eight-item close checklist against the client's ledger (Xero, MYOB Business or
QuickBooks Online): every bank and card account reconciled to a statement
dated at period end, nothing uncoded or in suspense, aged receivables and
payables equal to their control accounts, the month's pay runs posted, every
accrual and prepayment on the business's schedule proposed, the GST control
account agreeing with the return figure, and every clearing account at zero.
Each item is recorded as pass, fail or could not check, with the ledger read
it came from and its as-of time. Differences are reported to the cent and
never judged small enough.

Then the month waits for a named person. Nothing is written into the ledger
until the reviewer signs off and approves the journals. After that the
approved journals post once each under their intent id and read back, the
reviewer gets one task to set the lock date by hand (no ledger's API writes it
as at 12 November 2026), the next run reads the lock date back, and the closed
month is handed to the Recurring Report once.

It never reconciles, never recodes a line, never invents an amount, never
posts a journal nobody approved, and never moves a lock date backwards. The
lock date is only written by the build on a ledger that has been proved, on
the business's own file, to write it and read it back; none of the three does
today.

How it differs from Close Check: Close Check (recurring-report standard)
publishes a Ready or Not ready report for a Xero file. Month Sign-Off is the
close itself to the month-end-close standard: evidence per item on any of the
three ledgers, accruals from the schedule, a recorded sign-off by name, and
the post-sign-off journals, lock task and hand-over.

    npm install
    node run.mjs        # the conformance run; writes manifest.json and envelope.json
    node mutants.mjs    # every scenario must go red for a do-nothing build and a broken one

The committed evidence is in ../evidence/month-end-close/.

# month-end-close-build-standard: conformance harness

Generated by `npx @aipathway/conformance init month-end-close-build-standard`.

    npm install
    node run.mjs

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## This standard

13 checks: 11 provable here on the stub, 1 only in
production, 3 partial, 1 preconditions needing evidence rather than code.

The checks are fetched at run time from https://aipathway.com.au/explore-ai/month-end-close-build-standard,
so a correction published there reaches you without a release here.

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

This standard has no hosted provider, so `conformance connect` does not apply to it.

No hosted step. The build connects straight to the business's own ledger through the ledger's own sign-in, and the production check runs there: the approved journals and the lock date written and read back after a person's sign-off. There is nothing to buy: your build does this step on the business's own systems. No production run is offered yet, because the live port map is not published, so do not run AIPATHWAY_ENV=production. Run the pass test by hand on the real systems and attach the evidence.

The checks that never go green on the stub report `with_us`.
