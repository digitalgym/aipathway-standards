# Claim Clock

When a subcontractor's payment claim lands, Claim Clock works out the date the
payment schedule is due under the security of payment rule for the state the
job is in, and reminds the named person. It is kept as a compliance calendar to
AIP-BS-COMPLIANCE-CALENDAR 2026-10-03: each claim is one obligation, its anchor
is the date the claim was served, and the due date is derived each run from the
business's own dated rule for that state (business days, public holidays, the
Christmas closure the Act names, and the contract's shorter period where the
claim carries one). Nobody types a due date in.

The reminder goes to the claim's exception owner through the exception desk,
with the date, the rule version and a Done link, from the day the claim lands
and every run once the date has passed. A Done reply counts only with the
served payment schedule attached, filed and read back by obligation id. A
decision to serve no schedule and pay the claim in full is dated, and the claim
stays live. A missed date is never cleared, even when a schedule is filed late.
A claim with no served date, or on a job in a state with no rule, is surfaced to
a person and never given a guessed date.

The payment schedule is a legal instrument. This build drafts one against the
claim and holds it: a named person sets the scheduled amount and the reasons,
releases it and serves it. Nothing is sent and nothing is paid from this build.

The fixtures in `scenarios.mjs` are illustrative business-day counts, not legal
advice and not a statement of the current law in any state.

## Proving the scenarios can fail

Before the committed run, the scenarios were run against a do-nothing build and
thirteen broken builds (each the real build with one line changed). Every check
claimed as pass or shape_only went red for the do-nothing build and for at
least one targeted broken build:

| check | red under |
|---|---|
| 1 dates derived | do-nothing; keeps the first date it saw; uses the register's calendar date, not the business-day count; sends no reminder |
| 2 superseded versions | do-nothing; reads one state's rules for every claim; skips the history check |
| 3 per jurisdiction | do-nothing; ignores the public holiday in the rule; reads one state's rules; uses the calendar date; sends no reminder |
| 4 unknown anchor | do-nothing; defaults a missing served date to today |
| 5 evidence | do-nothing; accepts a bare Done as a served schedule; reminds a filed claim; sends no overdue reminder |
| 6 refusal | do-nothing; closes the claim on a decision to pay in full; sends no overdue reminder |
| 7 notice | do-nothing; releases its own draft; ignores an open exception |
| 8 breach stays | do-nothing; reminds a filed claim as overdue; sends no overdue reminder |

# compliance-calendar-build-standard: conformance harness

Generated by `npx @aipathway/conformance init compliance-calendar-build-standard`.

    npm install
    node run.mjs

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## This standard

10 checks: 8 provable here on the stub, 1 only in
production, 1 partial, 1 preconditions needing evidence rather than code.

The checks are fetched at run time from https://aipathway.com.au/explore-ai/compliance-calendar-build-standard,
so a correction published there reaches you without a release here.

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

This standard has no hosted provider, so `conformance connect` does not apply to it.

No hosted step. The production check runs against the calendar and document store already in use. There is nothing to buy: your build does this step on the business's own systems. No production run is offered yet, because the live port map is not published, so do not run AIPATHWAY_ENV=production. Run the pass test by hand on the real systems and attach the evidence.

The checks that never go green on the stub report `with_us`.
