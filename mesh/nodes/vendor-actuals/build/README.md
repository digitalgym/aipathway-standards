# invoice-check-build-standard: conformance harness

Generated by `npx @aipathway/conformance init invoice-check-build-standard`.

    npm install
    node run.mjs

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## This standard

11 checks: 9 provable here on the stub, 1 only in
production, 2 partial, 1 preconditions needing evidence rather than code.

The checks are fetched at run time from https://aipathway.com.au/explore-ai/invoice-check-build-standard,
so a correction published there reaches you without a release here.

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

This standard has no hosted provider, so `conformance connect` does not apply to it.

No hosted step. The production check runs against the job system and ledger already in use. There is nothing to buy: your build does this step on the business's own systems. No production run is offered yet, because the live port map is not published, so do not run AIPATHWAY_ENV=production. Run the pass test by hand on the real systems and attach the evidence.

The checks that never go green on the stub report `with_us`.

## Vendor Actuals

This folder is the build for the Mesh Directory node `vendor-actuals`. After
`npm install`, run `npm install --no-save ../../../../packages/conformance` so
the run uses the runner in this repo.

Before the committed run, every scenario was run against a do-nothing build
(checks 1 to 9 red) and against broken builds, each of which turned at least
one claimed check red: reporting the last failure instead of the first (1, 3),
matching a nearby PO (2, 4), trusting a verbal approval or skipping the
variation check (3), routing to two queues (1 to 4), hiding clean matches
(4, 5, 7, 9), paying a clean match (7, 8), hard-coding tolerances (9), a
percentage with no source on the exception (1, 3, 6), recording only the
outcome (8, 9), and treating a missing document as done (4).
