# duplicate-bill-hold-build-standard: conformance harness

Generated by `npx @aipathway/conformance init duplicate-bill-hold-build-standard`.

    npm install

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

Two read-only tools on the AI Pathway connector read the ledger for this check: list_bills returns the bills awaiting payment and list_paid_bills the bills paid since a day, with the supplier's contact id, invoice number, dates and total. Paid bills are read from Xero today. Neither reads supplier bank details yet, so rule 5 runs on the business's own data (its own ledger connection or a supplier list it exports) until the connector does. Call it on the AI Pathway MCP (office_voice.list_paid_bills): the owner mints a key at connect.aipathway.com.au/app/keys with the scope the tool names, on any AI Pathway account. There is no production run of these checks yet, so the stub run is the finished build; AIPATHWAY_PROVIDER=office_voice.list_paid_bills needs a live port map that is not published. Do not hand-roll the write.

The checks that never go green on the stub report `with_us`.
