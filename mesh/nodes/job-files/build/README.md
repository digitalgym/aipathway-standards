# Job Files: knowledge-base-build-standard conformance harness

Job Files puts every permit, approval, inspection certificate, procedure,
template, rate sheet and code on a building company's shared drive on one
register with a named person as owner, a checksum and the edition the issuer
printed. Each job's files sit in the folder named by the job system's job_id
(`Jobs/<job_id>/`), and the owner of a job's files is that job's supervisor
from the owner sheet. Only registered, current, non-customer files are indexed,
page by page or second by second. Search, across the company or scoped to one
job, returns the exact page of the exact file and composes nothing. A scheduled
watch re-fetches every registered file, catches an amended approval by its
checksum and tells the owner the same run.

`jobSheet()` in `build.mjs` reads one page per job off the register: the job's
current files with owner, edition and the locator that opens each, the
company-wide instruments it works under, and the open tasks for that job. In
production it is written as one Doc into the job folder and its file id read
back (report.published). The standard's checks do not score the sheet; they
score the register, the index, the watch and the handover it is read off.

Answering a question in sentences is not this build's job. That is the Cited
Answer standard, over the graph this register feeds.

Generated by `npx @aipathway/conformance init knowledge-base-build-standard`.

    npm install
    node run.mjs

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

This standard has no hosted provider, so `conformance connect` does not apply to it.

No hosted step. The production check runs over the business's real drive and mailbox with its real owners. The watch is the part not to hand-roll: a scheduled re-fetch and checksum compare of every source, with the owner told when it moves. It is a schedule and a table, not a product. There is nothing to buy: your build does this step on the business's own systems. No production run is offered yet, because the live port map is not published, so do not run AIPATHWAY_ENV=production. Run the pass test by hand on the real systems and attach the evidence.

The checks that never go green on the stub report `with_us`.
