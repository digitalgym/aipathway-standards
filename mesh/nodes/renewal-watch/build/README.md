# Renewal Watch

A compliance calendar for a small Australian business, built to
AIP-BS-COMPLIANCE-CALENDAR 2026-10-03. It keeps the renewals and services a
business carries on its own sites and its own name (test and tag, fire
equipment servicing, workers compensation, public liability, business name and
licence renewals) as dated rules per state or territory applied to an anchor
date. It derives every due date, drafts the booking or renewal inside the lead
time and holds it for a named person, files certificates as evidence by
obligation id, records a refusal as a dated outcome, and never clears a breach.
It sends nothing.

The fixtures in `scenarios.mjs` are illustrative intervals, not a statement of
what any Act or code of practice requires. The business keeps its own rule set.

## Proving the scenarios can fail

Before the committed run, the scenarios were run against a do-nothing build and
ten broken builds (each the real build with one port wrapped). Every check
claimed as pass or shape_only went red for the do-nothing build and for at
least one broken build:

| check | red under |
|---|---|
| 1 dates derived | do-nothing; a build that keeps the first due date it saw |
| 2 superseded versions | do-nothing; one that reads only the current version; one that reads one state's rules; one that raises nothing |
| 3 per jurisdiction | do-nothing; one that reads one state's rules for every site |
| 4 unknown anchor | do-nothing; one that never marks or raises an unknown anchor |
| 5 evidence | do-nothing; one that accepts a tick as evidence; one that forgets breaches |
| 6 refusal | do-nothing; one that closes the obligation on refusal |
| 7 notice | do-nothing; one that auto-releases its own drafts; one that ignores an open exception |
| 8 breach stays | do-nothing; one that forgets breaches; one that raises nothing |

# compliance-calendar-build-standard: conformance harness

Generated by `npx @aipathway/conformance init compliance-calendar-build-standard`.

    npm install
    node run.mjs

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## This standard

10 checks: 8 provable here on the stub, 1 only in
production, 1 partial, 1 preconditions needing evidence rather than code.

The checks are fetched at run time from https://aipathway.com.au/explore-ai/compliance-calendar-build-standard,
so a correction published there reaches you without a release here.

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

This standard has no hosted provider, so `conformance connect` does not apply to it.

No hosted step. The production check runs against the calendar and document store already in use. There is nothing to buy: your build does this step on the business's own systems. No production run is offered yet, because the live port map is not published, so do not run AIPATHWAY_ENV=production. Run the pass test by hand on the real systems and attach the evidence.

The checks that never go green on the stub report `with_us`.
