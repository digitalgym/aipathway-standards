# Loan Intake

The front desk for a credit adviser's office, built to AIP-BS-ADVICE-FILE.
When a lead or client interview lands, it builds the one client file in the
broker's CRM that the next person can pick up:

- the recording and transcription notice first, and no file at all when the
  client refuses (a person types the notes);
- every line kept verbatim with its span before any field is written;
- only the CRM's published keys written; addresses, employers and lenders
  resolved by lookup; a figure said unclearly parked as a gap
  (`asked_unclear`), never guessed;
- one file per client, updated by its id on every later call;
- completeness read back from the CRM, and one task per blocking gap (a missing
  figure or document) with the broker's name and a due date, raised once;
- lender policy answered only from a dated clause a named person accepted, or
  declined to the Head of Credit;
- a draft for internal approval that stays `blocked` while a gap or a source is
  open, and is never sent by the bot. No product is selected here.

It does not assess suitability, recommend a product or tell a client a
document is verified. Those stay with a person. Australian credit-licensee
terms throughout (responsible lending, not unsuitable, genuine savings). The
live write into the network's own CRM tenant and dated panel library is the
step not to hand-roll; it is `with_us`.

## Negative controls

Before the committed run, the scenarios were run against a do-nothing build
(checks 1 to 12 red) and against broken builds, each of which turned its check
red: consent recorded after capture, or a refusal ignored (1); no verbatim
(1, 2, 11); completeness not read (3, 4, 6, 9, 10, 11); spoken values
transcribed instead of resolved (4); a new file per interview (5, 6, 9); a task
re-raised on every call (6); retired and unaccepted clauses treated as live (8);
a remembered clause with the library detached (12); every draft marked ready,
or sent by the bot (9); no escalation (1, 10); no coaching (10, 11); no read
back by interview id (11).

## Survives the builder (check 13)

Declared, not scored: the Head of Credit can explain what it does from this
README and the standard; the file, the panel library and the tasks run on the
network's own CRM tenant and accounts.

# advice-file-build-standard: conformance harness

Generated by `npx @aipathway/conformance init advice-file-build-standard`.

    npm install
    node run.mjs

Every check starts red. That is the point: going green is the work, and a green
run means something because a red one was possible.

## The three files

| file | whose | what |
|---|---|---|
| `build.mjs` | yours | the build. The only file that does the job |
| `scenarios.mjs` | yours | one `holds` per check. Generated with the check's own words |
| `run.mjs` | ours | fetches the checks, runs, prints. No edits needed |

## This standard

14 checks: 12 provable here on the stub, 1 only in
production, 2 partial, 1 preconditions needing evidence rather than code.

The checks are fetched at run time from https://aipathway.com.au/explore-ai/advice-file-build-standard,
so a correction published there reaches you without a release here.

## The second run

There is no second run for this standard yet. Its live port map is not
published, so this folder has no `ports.mjs`, and `AIPATHWAY_ENV=production`
is refused rather than rerunning the stub under a production label. The stub run
is the whole of what can be proved here.

This standard has no hosted provider, so `conformance connect` does not apply to it.

No hosted product. The live write into the network's own CRM tenant, against a dated panel library it controls, is the step not to hand-roll, and it is quoted as a scoped build. Send the failing check id for a fixed price; do not build the live step yourself.

The checks that never go green on the stub report `with_us`.
